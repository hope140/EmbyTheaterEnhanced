## Fixed diagnostic contract

Only a fixed `stage`, fixed `reason` and optional integer HTTP status100..599 may leave a failure path. Current-context/current-probe, next-metadata/next-context/next-probe/next-prefix, progress and lifecycle are distinguished. Examples include source-cross-origin, container-unsupported, file-options-unproxied, metadata identity/source-count/direct-stream refusals, redirects/auth/non206, bad range, missing/weak/invalid ETag, mismatched length/encoding/validator/representation, network interruption and timeout. Unknown exceptions become a fixed fallback. URL, Location, pathname, identity values, ETag, UA/header/cookie/token contents, response bodies and arbitrary exception text are not reported.

Current-source failures stay attached to their request owner. A known current-proxy refusal is reported before fetching next metadata. Later unrelated errors cannot replace it. Cancel/retire/candidate replacement clears the owned diagnosis, and late failures cannot overwrite a new request. Frontend and main emit only these finite records through the existing diagnostics logger.

## Historical missing-ETag date prototype — removed

A missing ETag is an observed qualification failure, not evidence of a redirect or resolver failure. The pinned CD2 protocol currently exposes only path, size and regular-file type; it does not supply a stable content ID, modification time or content hash. Path/size, a signed session URL and its expiry are not substituted for a version.

The new limited fallback accepts only an absent ETag header (never an empty, weak or malformed tag) on an existing main-authorized CD2 transport with a safe positive size freshly obtained from Find. Exact206/range/identity encoding and HTTP total must match that size. A canonical Last-Modified and response Date must satisfy a conservative60-second gap and sane clock bounds. This uses the HTTP strong-date inference in [RFC9110 §8.8.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-8.8.2.2), which also assumes honest response metadata and a reasonable common-clock/skew basis; the time gap alone is not proof of immutability. Every subsequent origin read sends the real date in If-Unmodified-Since and If-Range, and still requires exact206, unchanged LM/total and eligible Date.200/412, changed validator kind, LM or size refuse without unconditional retry or new committed bytes.

Date and ETag records have separate typed identity keys. Date does not enter the key as a changing response timestamp. The proxy emits the actual Last-Modified and completely omits ETag for date records; no synthetic ETag is created. Actual B still needs fresh resolver authorization and a fresh HTTP validator probe before a prefix hit. URL refresh must return a new Find size equal to the known size before its URL is committed, then HTTP reads recheck the same typed validator. Account/document/generation isolation, sharedP, physical cancellation, original playback fallback and unplayed cleanup remain unchanged.

Missing LM/Date, unsafe date metadata or missing main file size now have distinct finite reasons. No dates or headers are exposed by these diagnostics. Current settings position is the existing **video settings → Advanced → 预载** section, with no new entry. Name, default-off70%/300MB, all options and next-play application remain unchanged.

This does not make every no-ETag source safe. Same-size replacement that dishonestly retains the same LM cannot be detected by this protocol, just as a dishonest unchanged ETag defeats an ETag cache. Sources without any qualifying HTTP validator remain unsupported for cross-request fragment reuse. A complete file downloaded from one response can instead be an internally consistent snapshot only if it fitsP; a general single-response partial stream cannot satisfy MKV tail/index/backward seeks without buffering beyondP or opening new unvalidated responses. That would require a separate stream-owner/fallback design, or a real provider immutable-version/hash contract, and is not hidden in this small validator change.

Current controlled evidence separates strict parser/conditional HTTP tests, authorized cache/refresh tests, and maintained Alameda/PM scenarios with synthetic helper/document. The no-ETag/date positive follows real progress and naturalEOF through the original nextTrack to a B prefix hit. The no-ETag/no-LM negative preserves original source/UA/A bytes and zero B requests/disk writes. These are not proof that the actual NAS supplies qualifying dates, nor current-source GPU/Windows/ordinary-install acceptance. No real credentials or business-source requests are used in these checks.

## No-validator alternatives and bounded scope

RFC9110 allows strong-date inference only with a justified shared-clock or sufficient-skew basis. The removed prototype's60-second gap and allowed five-minute future Date did not establish that basis for arbitrary CD2-returned origins. A same-second, same-size change with different origin/backend clocks and ignored conditions could pass its metadata comparison. That counterexample now stops at its first response: no date proof, no second fragment, no cache identity or committed prefix.

| Option | Consistency scope | Main limitations and cost |
| --- | --- | --- |
| One live response plus bounded prefix | Preload and subsequent sequential reads consume the same response; no reconnect/fragment merging | Seek only within retained bytes or forward stream position. MKV tail/index then backward seek can require unavailable bytes. Foreground physical cancellation must discard the partial prefix. A transferable next-response owner, EOF/generation handoff, backpressure scheduling and pre-decode fallback require a separate bounded experiment; not a drop-in daily MKV fix. |
| Complete single-response copy, only when whole file≤P | Seal all received bytes before playback; arbitrary Native ranges then read the same complete local copy | Not useful for a file>P. Partial/incomplete copies are discarded rather than resumed. This pins the representation selected at prefetch time, not a falsely proven latest remote version. Needs a next-owner/sealed-file handoff plus no-cache current-source forwarding that can observe and preempt background reads. Moderate implementation and real-helper validation, no kernel change or new capacity knob. |
| Genuine upstream validator or immutable-version binding | Existing bounded prefix/range reuse | A real strong ETag, or a verified contract binding the returned media representation to an immutable object version, is needed. A separate file hash, stable path, size or signed URL alone does not prove each partial response belongs to that version. Current locked CD2 fields do not provide such an attestation. |

A one-response transfer prevents client-side cross-response splicing; it is not proof that an upstream server never mutates the response's underlying file in place. A complete local copy is internally consistent with the received response and can be sealed locally, but without an upstream version it cannot claim freshness against a later remote replacement. None of these alternatives is enabled by this safety correction.

Recommended next experiment, if selected: first prove a file≤P complete-copy owner and natural original-PM handoff with synthetic current-source qualification, then separately add the current no-validator transparent-forwarding/physical-preemption path before any actual no-validator NAS acceptance. The real current source is also no-ETag; omitting that second step would leave the current-proxy prerequisite unsatisfied. For a target file>P, do not present this bounded experiment as a solution. Existing70%/300MB options and P accounting remain unchanged.
