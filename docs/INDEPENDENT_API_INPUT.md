# Fixed API maintenance input

The local candidate selects four AMD modules (`apiclient`, `mit-apiclient`, `transport`, `events`) plus their complete MIT notice under the original `modules/emby-apiclient/` path. Inputs are pinned to Emby.ApiClient.Javascript commit `fdd0939ac596406ab92274f30fd83d226a677424`, with original bytes/Git blob identities in `src/web-api/INPUT_MANIFEST.json` and selected source/output hashes in `selection.json`.

`src/web-api/tools/prepare-base.py` reproduces the reviewed MIT-derived base sources from the four fixed licensed inputs; `build-amd.mjs` reproduces AMD outputs without npm installation. The compiler recipe retains the six-module research generation set, but its candidate CM outputs are not copied into the product. Only the four explicit selected modules enter `src/electronapp`; source-only build material is not a runtime module. The existing CM is transformed by `tools/patch-connectionmanager-transport.cjs` from an exact immutable baseline, changing only HTTP/probe transport. Other Web input bytes remain frozen. Existing ApiClientEx, Credentials, discovery/WOL, canonical module IDs and app/page/playback owners remain in place.

An integration adaptation preserves the existing `{name, options}` message-listener representation and replay. Existing behavioral lifecycle assertions remain applicable; prior byte-format comparisons describing the old transpiled source are replaced by fixed-source and deterministic-output checks for the new selected implementation. Local AMD integration and synthetic network tests do not certify actual server login, playback, a complete Electron client or Windows installation.

The Web `deleteItem` entry takes an item DTO. The maintained API overrides the MIT scalar-ID method, uses `DELETE Items/{Id}` before server 4.7.0.33 and `POST Items/{Id}/Delete` from that version, and delegates successful local invalidation to the existing `LibraryChanged` owner. Confirmation, navigation and failure alerts remain in the original Web delete helper; failed requests do not publish deletion or retry destructive calls. Run `node --test tests/apiclient-delete.test.cjs` for the frozen Web helper/API comparison against a loopback HTTP fixture, including the version boundary, 403/500 responses, cancellation and batch-endpoint preservation. `ETE_DELETE_API_SOURCE` optionally selects an external AMD file for the same assertions against a baseline. This fixture never accesses a real media service.

## Emby seek-thumbnail preview boundaries

The existing VideoOSD overlay accepts a nonempty `ThumbnailSet` even without chapter markers. It obtains the actual source ID from `PlaybackManager.currentMediaSource(currentPlayer)`, then qualifies both `Items/{id}/ThumbnailSet` and `Items/{id}/Images/Thumbnail` with that `MediaSourceId`. It never selects the first entry in an item's `MediaSources` as a substitute. Missing source identity or an unsupported scoped endpoint produces the time/chapter fallback; it does not retry against an unqualified default version. The public pre-4.1.0.26 empty-thumbnail behavior remains.

Each in-memory metadata request belongs to its player, item, server/address, current account/credential epoch, actual source and play session. Generation checks reject late successes/failures; source changes and OSD stop/release/pause/destroy retire pending requests. Cancellation uses the selected ApiClient/transport's existing `AbortSignal` path. A display-item metadata response must still own its context before it may update the OSD item/chapters. Empty results are reused; transient failures can retry. Images remain CSS URLs using the existing HTTP cache; clearing a bubble prevents obsolete image display but does not promise cancellation of every Chromium image-cache transfer. No separate disk image library, quota or TTL is introduced.

Reproduce the locked-input regression with `node --test tests/videoosd-thumbnails.test.cjs`. `ETE_THUMBNAIL_BASELINE=1` selects the immutable unpatched OSD for the same behavioral assertions (the independently maintained API remains selected). The suite uses a synthetic DOM/player plus selected AMD modules; one ephemeral loopback HTTP response verifies physical body cancellation and timer cleanup. These checks do not certify Windows visuals or any particular server's handling of the version parameter. Actual acceptance should check a generated ThumbnailSet without chapters, two editions with different previews, fast switching/stop/reopen, and account/server changes. A server must already provide thumbnail data; the client does not generate it.
