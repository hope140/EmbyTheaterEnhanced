# Release 编写与维护规范

## 面向用户的内容

Release 标题使用 `v版本 · 简短主题`，例如 `v0.3.10 · 稳定性维护测试版`。主题说明本版的实际用途，标题已准确时无需为了版式反复修改。正文采用[模板](templates/RELEASE_TEMPLATE.md)，发布前替换占位符并删除不适用段落。

正文依次说明以下内容：

1. **渠道和适用范围**：准确平台、正式版或 Pre-release；测试版说明手动下载，并链接当前正式版。历史版本采用“发布时为正式版”等表述，避免误称当前 Latest。更新检查与自动安装分开说明。
2. **本次更新**：用少量条目说明用户能感知的变化。局部修复不扩大成全面兼容或性能保证；纯验证版本说明代码沿用关系。
3. **已知问题**：列与本版有关的限制及必要验证缺口，详细矩阵链接到对应版本的核验文档。当前问题汇总链接可持续更新，不能替代历史版本的验收事实。
4. **下载安装**：安装包、对应 SHA-256、用户指南。URL 和文件名必须取自该 Release 的实际附件；历史文件名可能带提交号，不按当前命名习惯猜测。来源记录仅在真实存在时链接；没有校验附件的旧版如实写明缺失。
5. **项目说明**：简短说明非官方身份，链接许可及第三方来源说明。未解决的许可、对应源码或材料问题保持未解决，不因发布或哈希验证声称已获授权或全面合规。

版本、源码提交、完整哈希、CI 和包体统计以来源记录、校验文件和核验文档为准；正文保留理解更新和安全操作所需的信息。SHA-256 核对用于确认下载字节与发布值相符，不等同于数字签名、可信来源认证或许可审查。

## 发布前检查

- 对照准确 Tag、来源记录与实际资产，核对版本、平台、文件名和下载 URL；不能把 Source code 压缩包当作客户端安装包。
- 核对 Release 的正式/测试标志及 Latest 选择。Pre-release 不因版本号更高自动提升为正式版。
- 先让正文引用的新指南或核验文档在目标路径可读，再发布依赖这些路径的展示文字。检查 GitHub Markdown 的标题、列表、表格和链接。
- 区分公开 CI、材料测试、包体核验、安装、前台、真实播放与远控证据；未执行和 UNKNOWN 保持原意。
- 新发行的原始 notes、附件校验与准确来源按既有[构建与打包](PACKAGING.md)流程保存；本规范不改变构建、版本和发布授权流程。

## 已发布文案的维护

只修正有实质价值的错误、歧义或导航，不为统一模板批量重写所有历史版本。编辑前保存对象 ID、Tag、完整原始标题/正文、标志、时间及全部附件身份；为受影响对象准备逐项 before/after 和原因。

文字维护仅更新经过审核的 `name` / `body`。原 Tag、目标来源、草稿/测试标志、Latest 选择、创建/发布时间、附件及其哈希不随文案调整。对象的 `updated_at` 可随正常编辑改变。写入前检查无并发漂移，写入后逐字段回读；出现不符时停止，按保存原文恢复受影响字段，再核对其它对象。

**Release 网页正文与原始 `RELEASE_NOTES.md` 附件可能不同。** 原始附件及产品 Tag 保留发行时的字节和来源；后续编辑的是网页展示文案。记录受影响版本、修改目的与前后关系，不覆盖原始 notes、重新打 Tag、重传二进制或伪称新正文仍等于旧 Git blob。无法兼顾历史来源时，保留原始正文，在独立指南补充导航。
