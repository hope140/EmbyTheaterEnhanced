# Shared byte-range cache candidate

This independent candidate starts at the released `88578c91` source. It does not select the earlier complete-file download experiment. PlaybackManager still owns Item, MediaSource, PlaySession, queues, remote control and progress; the candidate changes only the final readable source when explicitly enabled and verified.

## Confirmed behavior

Next-episode progress choices are 50/60/70/80/90%, default 70%. Prefix preload choices are 100/300/500 MB, default 300 MB (1 MB = 1,000,000 bytes). The last actually playing video's cached ranges survive Stop and a normal application exit, without a time expiry. They are retired only when another video actually starts; a browser selection or preload is not playback. Existing readers must release before their bytes are deleted. An unplayed next-episode preload is discarded on exit. These controls do not change `mpv-demuxermaxbytes`, mpv memory buffering, playback progress or the existing RAM-buffer setting.

## Byte transport and index

The async store records immutable raw blocks and a digest-checked atomic JSON index, not demuxed mpv packets or mpv's temporary cache file. It retains only the actual last-played entry on normal close/reopen. A loopback-only HTTP reader serves normal GET, HEAD and single bounded/open/suffix Range requests. Cache hits return stored raw bytes; holes fetch only the required blocks from the current origin. It streams with backpressure rather than waiting for a complete file. Prefix warming has a byte budget and explicit bandwidth limit; foreground misses interrupt background upstream reads. Aborted attempts consume the background network budget too.

Every source open requires a fresh authorized-origin 206 probe, a strong ETag and exact representation length. All subsequent misses use If-Match and validate ETag, Content-Range, length and identity encoding before committing a complete block. Weak/missing validators, ignored Range, unknown lengths, compressed bodies, redirects and authorization errors do not select a cache source. Redirects are not followed or given forwarded credentials. The first scope is static HTTP(S) files on the authenticated Emby origin; local mounts, cross-origin CD2/STRM targets, live/HLS/transcoded streams remain on their existing source. Changing signed authentication parameters requires a fresh probe; server/account/media-source/representation identities remain distinct. URLs, credentials and play-session tokens are not stored in the disk index.

Routes contain an in-memory random routing capability, bind only `127.0.0.1`, reject browser Origin/Referer and unexpected Host, and never accept an arbitrary upstream target from a client URL. Stop/cancellation retires routes, interrupts owned requests, waits for their readers and then releases storage leases. Normal exit discards unplayed next data. The current v2 store holds a deterministic root-scoped loopback bind as an OS-lifetime ownership guard. It accepts no commands or media; connections are immediately closed. Conflicts disable caching without touching another writer. Only while holding this exclusive guard may it recover a leftover v2 disk marker and clean orphan interrupted block/index writes. Earlier v1 experimental roots are refused rather than modified. The independent-process regression excludes a second writer, kills only the owned fixture process, waits for its actual exit, and reopens the committed ranges. Windows ownership/recovery still requires its own runtime check.

## Occupancy and evidence boundaries

Total raw cache bytes and minimum free space require explicit configuration; no production disk quota or bandwidth default is inferred from the existing mpv RAM setting. Quota includes the last object, next prefix and any readers still retiring. Atomic writes add at most one temporary block plus bounded index metadata. At quota or disk pressure, valid foreground reads continue without storing additional bytes; preloading stops. This bounds disk use but does not promise to retain every byte of an arbitrarily large movie. The retained object's lifetime has no TTL.

The foundation store/transport and confirmed choice schema are executable with `node --test tests/playback-range-cache.test.cjs`. Tests use temporary private roots and tiny loopback data, including real HTTP reads, fresh-URL reopen, tail seeks, cancellation, identity/version mismatch, corruption, capacity and foreground preemption. Those library tests alone do not establish app launch, settings, true playback-start promotion or queue integration; the additional controlled app integration is described below. No test downloads real media, accesses a NAS, changes a server or uses private account data. Warming starts at raw offset zero; it does not guess a resume/skip-intro time. Partial prefix warming does not guarantee a particular number of decoded seconds: container indexes may require a tail seek which is fetched on demand.

## Controlled app integration

The next integration commit adds a real, default-off application entry. Supply all three arguments: `--ete-range-cache-trial`, `--ete-range-cache-config=<absolute JSON file>` and `--ete-range-cache-profile=<absolute private directory>`. The profile must be empty or carry this trial's own marker; ordinary profiles are refused. Before bootstrap, appData/userData/sessionData plus APPDATA, LOCALAPPDATA and MPV_HOME are isolated. The JSON requires explicit `maxBytes`, `minFreeBytes`, `bytesPerSecond` and `timeoutMs` (1–30000); optional `progressPercent` and `preloadMB` use the confirmed choices/defaults. There is deliberately no formal disk-space or network-speed default, and ordinary launches remain disabled. The normal settings page is not changed by this controlled entry.

The maintained adapter captures identity from its existing ConnectionManager/ApiClient and actual current Item/MediaSource/PlaySession, then sets a generation-bound main-process context. The existing helper command still performs loadfile; only the final verified HTTP source becomes a loopback range source. Native `core-idle=false`, already validated/attributed by the controller, confirms actual playback and queues retention before an immediate Stop can release its lease. An unsupported static origin stays on its original source; a missing or changed validator during a proxy read is an error, never a splice of incompatible bytes. There is no claim of seamless automatic restart after a midstream origin failure.

The renderer reads `_playQueueManager.getNextItemInfo()` without invoking the asynchronous `nextItem()` API or changing the queue. Only a definite same-series Episode can warm, after the selected progress threshold; the service also checks actual helper time-pos/duration. Metadata uses the current selected ApiClient's authorization provider and a bounded, cancellable same-origin request. A single confirmed source with direct-stream capability is required; ambiguous editions are skipped. Credential/provider/account/server changes are checked every 500 ms and retire the owned work; original session reporting remains unchanged. Cancelling an old renderer binding cannot retire the new generation.

Stopping or switching generations cancels downloads and releases readers but can keep the already committed next prefix within this process, allowing the real Stop → begin-generation → loadfile handoff to consume it. Queue changes discard the obsolete prefix; actual next playback promotes it; another actual video or application exit discards the unplayed prefix. Current-source misses preempt background range reads. When the current source cannot use this verified transport, automatic preloading is skipped because its bandwidth priority cannot be observed by this layer.

The integration regression uses the real selected AMD ApiClient, real loopback HTTP/cache/session, maintained native service/client, and an explicitly mocked helper. It verifies threshold gating, retirement handoff, empty/multiple-source skips, credential change, actual-play promotion and immediate Stop. It does not execute the fixed Windows DLL. For a separate real local decoder/player check, use only existing absolute tool paths and a new output directory:

```sh
node tools/playback-range-local-smoke.cjs --ffmpeg=/absolute/ffmpeg --ffplay=/absolute/ffplay --out=/absolute/new-empty-output
```

This generates a synthetic MP4, compares local-file and range-source frame MD5 output, then runs FFplay with dummy video/audio drivers and isolated profile variables. Its 64 KiB store must remain a partial cache of the larger generated file. The receipt binds the clean source commit and tool hashes. It is FFmpeg/FFplay evidence, not fixed libmpv, visible Windows output, subtitles, Session/remote-control acceptance, real Emby/NAS access or an installation/package result.


## Conditional requests and ownership recovery

The local reader uses normal HTTP If-Range behavior: an ETag mismatch ignores Range and sends the full current representation; a matching ETag preserves 206. Origin missing/weak ETags, bad Content-Range and unstable representation lengths remain ineligible. A progress update racing a backward seek returns a pending state, allowing the next genuine threshold crossing to retry rather than permanently suppressing that next episode.

The v2 store's additional loopback bind is only a process-lifetime ownership guard, released after file work settles or by OS process teardown. It does not share a port (`reusePort` is false), does not retry a collision, and does not run outside this application's lifetime. Node's [Net listen contract](https://nodejs.org/api/net.html#serverlistenoptions-callback) documents these bind/conflict options; Linux child-process recovery tests are separate from the still-required Windows verification. Concurrent close callers share completion, and storage leases must be released before normal close.

The [source matrix and resource decisions](PLAYBACK_RANGE_SOURCE_MATRIX.md) distinguish current direct-source eligibility, original-source dispatch for redirects/header-dependent origins, and an error after an already-selected source changes representation. They also separate the confirmed 70%/300 MB behavior from explicit trial disk, free-space and bandwidth limits. No real proxy or server compatibility is inferred from the local fixtures.

## Explicit startup and pending-next ownership

Main validates explicit trial intent before bootstrap. A missing/invalid trial configuration, absent profile directory, wrong ownership marker, unsupported trial option form or duplicate enable switch stops startup with the fixed `range-cache-trial-launch-invalid` reason. It does not become a normal-profile launch. A valid trial owns appData/userData/sessionData and child profile variables before any product data initialization, and bypasses the later legacy Windows positional userData override. Launches without trial options retain the existing Host positional-dataPath behavior.

`tests/playback-range-startup-isolation.test.cjs` executes the entire maintained main source with Electron/native boundaries replaced, a Windows-platform/Host-argv contract and real bootstrap/DeviceId writes inside private temporary trees. It checks the later parser, STRM root, ready-time window-state read, kernel root, child environment and unchanged ordinary-profile canaries. The raw Windows-literal case does not access that literal path. It is a startup-order/file-ownership regression, not an actual Windows Electron/Host launch. Optional `ETE_RANGE_MAIN_SOURCE` and `ETE_RANGE_LAUNCH_SOURCE` select only comparison source bytes for the same assertions.

A preload candidate also has an epoch independent of the playback generation. Cancel-next, context retirement and a newer preload retire a pending time-pos/duration gate; the gate rechecks ownership after both properties settle and before claiming the next slot. Helper/endpoint/generation guards remain. The in-memory full-service/session regression covers cancel-before-reply, pending replacement in both response orders, delayed old-helper values and late property rejection. This invalidates stale results; it does not claim physical cancellation of the existing native property requests, which retain their normal deadline/exit handling.

The [fixed Windows/native smoke procedure](PLAYBACK_RANGE_WINDOWS_SMOKE.md) supplies preparation and explicit hidden execution commands for the existing source-built candidate. It distinguishes two-process retained-range consumption from in-process memory buffering and leaves actual Windows/native, visual and server outcomes pending execution. Its small quota/bandwidth settings are test inputs only.

## Test-package boundary

Fresh builds include the locked same-archive Electron loader beside libmpv, with its exact source/target relation enforced by runtime provenance and the package gate. This is a new build identity, not a patch to the historical candidate. Ordinary launches still disable the trial; explicit isolated-profile/config arguments above are necessary. There is currently no visible threshold/size/settings, preload-progress or cache-management entry. The queue/progress adapter exists, but the hidden current-media populate/reopen smoke does not call next preload or exercise the real renderer/UI. Those require separate controlled app acceptance, and real sources may remain ineligible under the current strict redirect/authentication/validator contract.
