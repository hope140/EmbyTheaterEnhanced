# Published v0.4.3 Native playback close check

This independent validation consumes release 423094961, installer asset 673841569, source `69e55b91a0cc6ba4b01ce60cb65d9aca41b0311e`. The installer SHA256 is `0696b9f6f2c2ed845c9124771bea2a7462532908c2ddbb9ecdaca59271c6b266`. The existing checker validates the successful original build, current tag, all five official release assets, provenance, installed manifest and every original payload file. It performs a normal installation in a fresh hosted Windows runner and starts the installed shortcut's Host with its original arguments.

No release or original installed file is changed. One temporary AMD script is added to the installed `scripts` directory, whose ordinary loader reads it before `appready`. It waits for that actual event, then uses the existing trusted renderer IPC to create the production Native endpoint and play a locally generated 60-second Y4M clip. Progressing time and decoded 32x18 video parameters are required. Real SMTC/preview state is sent through the existing channel; no Native, capture or FFI doubles are used in the Windows acceptance run. This stimulus does not test Emby login, PlaybackManager queue/session ownership or visible DWM appearance.

Only the Native `property-unavailable` response is treated as not ready within the existing 20-second playback/5-second Stop budgets. Other property and generation failures remain immediate failures; unavailable properties alone can never satisfy playback. Main-window selection excludes the nonactivating video carrier using its Windows extended style. Protocol-helper identity excludes the short-lived `--place-window-behind` helper, while the process inventory still tracks both roles and their descendants for exit verification.

Cases are playback directly followed by OS window close, confirmed Native Stop followed by close, and another playback/close in a new normal Host process. The report records PID, parent PID, creation time and relative image identity, including observed descendant processes. It checks at 2, 5 and 15 seconds after close, requiring Host/Electron/helper exit zero and no remaining owned process. Missing shutdown log persistence remains a separate diagnostic. Startup, decoding, preview or cleanup failures cannot pass.

Any failure is recorded before bounded cleanup. Cleanup is restricted to processes belonging to this unique installation or its observed descendants, checks creation identity, and uses previously retained process handles. Such cleanup forces the result to failed. The temporary script is removed only if its hash still matches; every original payload file is checked again. Raw logs and generated path-bearing scripts stay on the disposable runner; only the bounded report is uploaded.

Branch `validation/v043-native-exit` initially has `enabled:false` in `tools/v043-installed-startup-input.json`. A reviewed change to `true` starts the existing branch-bound installer-check workflow; it does not rebuild or publish. If the repository UI exposes dispatch for this workflow/ref, dispatch uses the same committed binding. A skipped/disabled run is not acceptance. The local stimulus tests use doubles only to check sequencing; actual Windows results must be reported separately.
